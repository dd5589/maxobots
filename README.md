# MAX-бот социальной поддержки «Забота о людях»

Интерактивный чат-бот в мессенджере **MAX**, который помогает разобраться с возможной причиной отказа в социальной выплате или мере поддержки и определить следующий шаг: что проверить, какие документы подготовить и куда обратиться.

## О проекте

Получение отказа в социальной выплате часто не означает, что пользователю понятно, **почему** ему отказали и **что делать дальше**. Информация о требованиях, документах и порядке действий может быть распределена между несколькими источниками.

«Забота о людях» решает конкретный участок этого пользовательского пути — **момент после получения отказа**.

Пользователь проходит короткий сценарий в MAX, отвечает на вопросы с помощью кнопок и получает персонализированную информационную карточку:

* возможная причина отказа;
* какие требования стоит проверить;
* какие документы подготовить;
* куда обратиться дальше.

Бот не принимает юридически значимых решений и не заменяет государственное ведомство или профессиональную юридическую консультацию.

## Проблема

Пользователю приходится самостоятельно:

1. найти информацию о соответствующей мере поддержки;
2. понять требования и условия;
3. сопоставить их со своей ситуацией;
4. определить, каких документов не хватает;
5. разобраться, в какую организацию или сервис обращаться дальше.

Это приводит к лишним переходам между источниками, повторным ошибкам и дополнительной нагрузке на первичную консультационную инфраструктуру.

Цель MVP — убрать ручное сопоставление информации в наиболее понятной точке процесса: **разборе причины уже полученного отказа**.

## Как работает бот

Пользовательский путь:

```text
/start
   │
   ▼
Выбор категории
   │
   ▼
Последовательный опрос
   │
   ├── доход
   ├── имущество
   ├── документы
   └── другие условия сценария
   │
   ▼
Scenario Engine
   │
   ▼
Сопоставление ответов с правилами
   │
   ▼
Итоговая карточка
   ├── возможная причина отказа
   ├── что проверить
   ├── документы
   └── куда обратиться
```

Основной пользовательский сценарий полностью проходит внутри MAX.

## Поддерживаемые сценарии

|Категория|Сценарий|
|-|-|
|Родитель|Разбор отказа в едином пособии на ребёнка|
|Студент|Разбор отказа в государственной социальной стипендии|
|Пенсионер|Разбор отказа в социальной доплате к пенсии|
|Участник СВО / ветеран / семья|Разбор отказа в специализированной мере поддержки|

Сценарии хранятся в декларативных JSON-файлах, поэтому добавление или изменение правил не требует переписывать основной runtime бота.

## Архитектура

Решение реализовано как самостоятельный бот без собственного публичного API и без обязательного Mini App.

```text
┌───────────────┐
│   Пользователь│
└───────┬───────┘
        │
        ▼
┌───────────────┐
│      MAX      │
└───────┬───────┘
        │ HTTPS Webhook
        ▼
┌──────────────────────────────┐
│       Node.js runtime        │
│                              │
│  ┌────────────────────────┐  │
│  │ Scenario Engine        │  │
│  └───────────┬────────────┘  │
│              │               │
│  ┌───────────▼────────────┐  │
│  │ Rules / Matcher        │  │
│  └───────────┬────────────┘  │
│              │               │
│  ┌───────────▼────────────┐  │
│  │ Session State / TTL    │  │
│  └────────────────────────┘  │
└───────────────┬──────────────┘
                │
                ▼
         MAX Bot API
```

### Основные компоненты

* **Bot runtime** — обработка сообщений и callback-событий MAX.
* **Scenario Engine** — управление переходами между вопросами.
* **Matcher** — сопоставление ответов пользователя с правилами, в том числе отдельный matcher для сценария единого пособия.
* **Session manager** — временное хранение состояния текущего диалога с TTL.
* **JSON data layer** — загрузка сценариев, причин и правил из `data/\\\\\\\\\\\\\\\*.json`.
* **Webhook layer** — приём событий MAX по HTTPS.
* **MAX Bot API** — отправка сообщений и работа с платформой.

## Production и Webhook

В production используется:

```env
NODE\\\\\\\\\\\\\\\_ENV=production
BOT\\\\\\\\\\\\\\\_TRANSPORT=webhook
```

Приложение принимает события MAX через HTTPS endpoint.

Схема:

```text
MAX
 │
 │ HTTPS
 ▼
/webhook
 │
 ▼
Node.js bot runtime
```

Для production нужен managed hosting с публичным HTTPS endpoint. В проекте подготовлена конфигурация через `Amvera.yaml`.

Приложение внутри контейнера слушает порт `10000`, а внешний managed hosting предоставляет публичный HTTPS URL.

### Amvera

Для deployment:

1. Создайте Web Service из репозитория.
2. Используйте Dockerfile проекта.
3. Передайте `BOT\\\\\\\\\\\\\\\_TOKEN` как secret.
4. Установите `BOT\\\\\\\\\\\\\\\_TRANSPORT=webhook`.
5. Задайте `MAX\\\\\\\\\\\\\\\_WEBHOOK\\\\\\\\\\\\\\\_SECRET`.
6. Убедитесь, что `MAX\\\\\\\\\\\\\\\_WEBHOOK\\\\\\\\\\\\\\\_DOMAIN` указывает на HTTPS origin сервиса.

После deployment ожидается запуск webhook примерно в таком виде:

```text
https://<service>.onrender.com/webhook
```

Подробности deployment находятся в:

```text
docs/DEPLOY\\\\\\\\\\\\\\\_MANAGED\\\\\\\\\\\\\\\_HOSTING.md
```

## Особенности интерфейса MAX

У MAX есть ограничения на отображение текста в inline-кнопках. Поэтому в проекте используются короткие подписи кнопок, а подробный контекст передаётся непосредственно в тексте вопроса.

Логика сценария не зависит от длины отображаемой подписи: callback содержит идентификатор/индекс выбранного варианта.

## Безопасность и хранение состояния

Бот не подключается напрямую к закрытым ведомственным системам.

В MVP отсутствуют прямые интеграции с:

* ЕГИССО;
* СФР;
* Госуслугами;
* другими закрытыми ведомственными системами.

Сценарии работают на заранее подготовленных данных и правилах.

Состояние текущего диалога хранится временно и очищается по TTL. Это не является полноценной системой долговременного хранения пользовательских данных.

Webhook защищён секретом, передаваемым через конфигурацию приложения.

## Ограничения MVP

Важно учитывать следующие ограничения:

1. **Результат бота — информационная подсказка.**  
Он не является официальным решением государственного ведомства.
2. **Бот не заменяет юридическую консультацию.**  
Пользователю необходимо проверять актуальные требования по официальным источникам.
3. **Нет прямой интеграции с ведомственными системами.**  
В MVP используются подготовленные JSON-справочники.
4. **Правила требуют актуализации.**  
Изменения законодательства, региональных параметров и требований должны отражаться в данных сценариев.
5. **Состояние сессии временное.**  
Перезапуск runtime может привести к потере незавершённой сессии.

## Масштабирование

Архитектура разделена на стабильное ядро и конфигурационную часть.

### Неизменяемое ядро

При добавлении новых регионов или сценариев сохраняются:

* Node.js runtime;
* scenario engine;
* matcher;
* логика пошагового диалога;
* взаимодействие с MAX Bot API;
* Webhook-механика.

### Адаптируемая часть

Меняются преимущественно JSON-справочники:

* региональные ведомства;
* контакты МФЦ;
* ссылки на региональные порталы;
* региональные коэффициенты;
* величины прожиточного минимума;
* локальные критерии имущественной обеспеченности;
* правила конкретных мер поддержки.

Следующим направлением развития может стать переход от анализа уже полученного отказа к **предварительной проверке условий и документов до подачи заявления**.
