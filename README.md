# MAX: помощник по социальной поддержке

MVP чат-бота и Mini App в MAX, который помогает пользователю разобрать отказ в социальной выплате и понять следующий шаг. Текущая версия содержит сценарий для родителей по единому пособию; архитектура подготовлена к добавлению студентов, участников СВО и пенсионеров.

## 1. Что делает решение

Основной пользовательский путь:

1. Пользователь запускает бота в MAX.
2. Бот задаёт последовательность вопросов о ситуации.
3. Backend сопоставляет ответы с заранее подготовленными правилами и формирует возможные причины.
4. Пользователь получает информационную карточку: возможная причина, почему она выбрана, что проверить, куда обратиться и какие документы подготовить.
5. Mini App показывает чек-лист дальнейших действий.
6. При необходимости пользователь может поставить напоминание.

Результат сценария не является официальным решением СФР или иного ведомства.

## 2. Архитектура

```text
MAX
 │
 ├── чат-бот
 │    ├── команды /start /restart /help
 │    ├── вопросы сценария
 │    └── напоминания
 │
 └── Mini App
      ├── карточка результата
      └── чек-лист
            │
            ▼
      Node.js HTTP API
            │
      ┌─────┴──────────┐
      │                │
  reasons.json     JSON runtime store
      │                │
      └───────┬────────┘
              ▼
          rule-based matcher
```

Ключевой принцип: бизнес-логика не зависит от конкретного интерфейса. В дальнейшем категории и сценарии добавляются как отдельные данные и правила, а не как набор несвязанных ботов.

## 3. Состав проекта

- `src/bot` — MAX-бот и пользовательские сценарии;
- `src/services/matcher.js` — rule-based разбор ответов;
- `src/services/reasons.js` — загрузка каталога причин;
- `src/services/storage.js` — хранение временного состояния диалога;
- `src/services/reminders.js` — хранение напоминаний;
- `src/services/jsonStore.js` — общий атомарный JSON-store для runtime-данных;
- `src/api` — HTTP API Mini App;
- `mini-app` — React/Vite Mini App;
- `data` — тестовый и контентный набор причин;
- `tests` — unit-тесты backend;
- `scripts/smoke.sh` — smoke-проверка запущенного стека;
- `scripts/check-repo.sh` — проверка, что в Git не попали runtime-зависимости и секреты;
- `openapi.yaml` — контракт собственного HTTP API;
- `.github/workflows/ci.yml` — CI.

## 4. Требования

- Node.js `20.19.0` или новее в ветке Node 20;
- npm;
- Docker + Docker Compose для воспроизводимого запуска всего стека.

## 5. Локальная установка

### Backend

```bash
npm ci
npm test
npm run lint
npm run check:repo
```

Создайте локальный `.env` на основе `.env.example`:

```bash
cp .env.example .env
```

Для локального запуска задайте минимум:

```text
BOT_TOKEN=...
ALLOW_DEV_AUTH=true
```

Запуск:

```bash
npm start
```

Backend: `http://localhost:3000`.

### Mini App

```bash
cd mini-app
npm ci
npm run dev
```

Mini App: `http://localhost:5173/`.

В development можно открыть, например:

```text
http://localhost:5173/?startapp=income_calc
```

`devBridge` передаёт `dev-init-data`; backend принимает его только при `ALLOW_DEV_AUTH=true` и вне production.

## 6. Docker

Один запуск всех локальных компонентов:

```bash
cp .env.example .env
# заполните BOT_TOKEN

docker compose build
docker compose up -d
```

Порты:

- backend — `3000`;
- Mini App/nginx — `8080`.

Проверка:

```bash
./scripts/smoke.sh
```

Остановка:

```bash
docker compose down
```

Повторный запуск:

```bash
docker compose up -d
```

Для reproducible build исходные `node_modules`, `.env` и runtime-файлы в репозитории не хранятся: зависимости устанавливаются через `npm ci`.

## 7. Переменные окружения

См. `.env.example`.

| Переменная | Назначение | Пример |
|---|---|---|
| `BOT_TOKEN` | токен MAX-бота | `***` |
| `MINIAPP_URL` | публичный URL Mini App | `https://example.ru/` |
| `PORT` | HTTP-порт backend | `3000` |
| `TZ` | часовой пояс runtime | `Europe/Moscow` |
| `MAX_INIT_DATA_MAX_AGE_SECONDS` | максимальный возраст `initData` | `3600` |
| `ALLOW_DEV_AUTH` | dev-only авторизация | `true` только локально |
| `CORS_ORIGIN` | разрешённый Origin | `http://localhost:5173` |
| `DATA_DIR` | каталог runtime-данных | `./runtime` |
| `SESSION_TTL_SECONDS` | TTL незавершённой сессии | `7200` |
| `MAX_ANSWER_LENGTH` | максимальная длина одного ответа пользователя | `2000` |

Рабочие токены и ключи не должны попадать в Git.

## 8. Работа с данными

### Контент

`data/reasons.json` — заранее подготовленный набор причин, действий и документов. Эти данные являются содержимым MVP и должны проверяться по актуальным официальным источникам перед использованием в продукте.

### Runtime

`DATA_DIR` содержит только временное/персистентное состояние MVP:

- состояние текущего диалога пользователя;
- запланированные напоминания.

Незавершённые сессии автоматически удаляются после `SESSION_TTL_SECONDS`. После завершения сценария сырые ответы удаляются отдельно; в state остаются только технический статус и выбранный результат. В напоминаниях не сохраняется текст пользовательских ответов.

Каталог `runtime/` исключён из Git. JSON-файлы создаются автоматически и записываются атомарно с ограниченными правами доступа.

Текущая JSON-модель предназначена для одностоечного MVP и не является заменой защищённой промышленной БД.

## 9. Внешние сервисы и интеграции

- MAX Bot API — взаимодействие чат-бота с MAX;
- MAX Mini App / MAX Bridge — работа Mini App внутри MAX;
- публичный HTTP API проекта — связь Mini App с backend;
- официальные источники социальной поддержки используются как основание для контента, но текущая версия MVP не выполняет реальную интеграцию с государственными информационными системами.

Если данные или интеграции в MVP модельные/тестовые, это должно быть явно указано в материалах проекта.

## 10. API

OpenAPI-контракт находится в `openapi.yaml`.

### GET `/health`

Возвращает:

```json
{"status":"ok"}
```

### GET `/api/meta`

Возвращает версию, дату обновления и список источников каталога причин.

### GET `/api/reason/{id}`

Требует заголовок:

```text
X-Max-Init-Data: <raw MAX initData>
```

### GET `/api/checklist/{id}`

Требует тот же заголовок и возвращает чек-лист шагов и документов.

Все authenticated API responses помечаются `Cache-Control: no-store`.

## 11. Проверка основного сценария

1. Открыть бота в MAX.
2. Выполнить `/start`.
3. Ответить на вопросы.
4. Ввести фрагмент текста отказа.
5. Убедиться, что показана возможная причина и дальнейшие действия.
6. Открыть Mini App через кнопку.
7. Проверить чек-лист.
8. Проверить напоминание.
9. Повторить сценарий через `/restart`.

Ожидаемый результат: сценарий можно пройти от начала до результата без ручного вмешательства разработчика.

## 13. Известные ограничения MVP

- текущий продукт покрывает один пользовательский сценарий — отказ в едином пособии на детей;
- интеграций с ЕГИССО, СФР и другими государственными ИС нет;
- runtime хранится в локальном JSON и рассчитан на один экземпляр приложения;
- актуальная документация MAX рекомендует Webhook для production; текущая JS-библиотека запускает бота через `bot.start()`/Long Polling, поэтому переключение на Webhook требует отдельного deployment-шагa после доступности публичного HTTPS endpoint;
- для собственного API перед финальной сдачей нужен `DATA-API.yaml` строго по официальной схеме организаторов; в исходном ТЗ в репозитории названия полей схемы не приведены, поэтому этот файл нельзя корректно угадать без шаблона организаторов.

## 14. Безопасность

- `.env` и любые другие секреты игнорируются Git;
- MAX `initData` проверяется по подписи и сроку актуальности;
- дублирующиеся параметры `initData` отклоняются;
- API требует авторизацию для данных причин/чек-листов;
- runtime-файлы не должны переноситься из реальных пользователей в тестовые фикстуры;
- тестовые данные должны быть синтетическими.

## 15. Остановка и очистка

Остановить Compose:

```bash
docker compose down
```

Удалить локальный volume runtime, если нужно начать полностью с чистого состояния:

```bash
docker compose down -v
```
